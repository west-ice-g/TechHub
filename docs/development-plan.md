## 1. 开发原则与阶段门禁

### 1.1 基本原则

1. 需求、数据库设计、架构和页面流程在前，编码在后。
2. 所有核心页面和后台操作必须连接 MySQL，不允许静态页面冒充。
3. 12 个功能模块均为 P0，不因赶工删减。
4. 每名组员至少独立完成一个 Model、一个 View、一个 Controller，并有真实提交记录。
5. 每个 PHP 文件有规范注释头，作者由实际编写者填写。
6. 所有数据库初始化 SQL 最终放入 `/data/install.sql`。
7. 安全要求落实在代码与测试中，不停留在文档口号。
8. 不伪造进度、测试通过、截图、分工、Git 提交或团队信息。
9. 先完成可演示的最小闭环，再优化视觉和扩展功能。
10. 任何表结构或权限变更同步更新文档和 SQL。

### 1.2 阶段门禁

每个阶段必须完成“交付物 + 验收检查”后才进入下一阶段。不能以“代码大概写完了”作为完成标准。

| 门禁 | 必须满足 |

```text

  → 统计
  → 测试修复
```

### 3.2 并行开发建议

- 数据库结构、核心框架和权限模型先由技术负责人定稿，其他成员基于同一接口开发；
- 业务模块可按工作包并行，但不能各自定义表结构、路由前缀或权限码；
- 前端布局和静态资源先统一，避免每人一套样式；
- 每完成一个模块，由负责人提供真实截图、SQL 验证和测试记录；
- 合并前执行 `php -l`、权限检查和数据库回归。

## 5. Git 与版本控制计划

### 5.1 初始化

当前目录**尚未初始化 Git**。经用户确认后执行：

```bash
git init
git add .
git commit -m "docs: initialize requirements and architecture plans"
```

当前禁止在未确认情况下使用不存在的历史记录冒充开发过程。

### 5.2 分支策略（建议）

| 分支/操作 | 用途 |
| --- | --- |
| `main` | 可演示、可提交版本 |
| `feature/<module>` | 单模块开发，如 `feature/articles` |
| `fix/<issue>` | 缺陷修复 |
| `docs/<topic>` | 文档补充 |

小团队可以采用主干 + 短分支；合并前检查冲突、SQL 变更和权限配置。

### 5.3 提交规范

建议使用 Conventional Commits 风格：

```text
feat(article): 增加文章发布与浏览量更新
fix(auth): 修复停用账号仍可访问后台的问题
docs(database): 更新留言审核字段说明
test(file): 增加危险文件上传拒绝用例
```

要求：

- 一次提交只做一件可说明的事；
- 不提交 `.env`、真实密码、上传文件、日志、数据库备份；
- 不提交 IDE 私有配置；
- 每名成员使用自己的 Git 身份提交自己实际编写的文件；
- 不补造日期、作者或提交记录；
- 合并前确认没有把示例数据误当真实团队资料。
